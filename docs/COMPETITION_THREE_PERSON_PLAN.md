# 上新图 Industry 微信小程序比赛优化与三人协作方案

## 一 项目结论

上新图不建议推倒重做。现有代码已经完成商品图片上传、AI 抠图、AI 商业场景生成、三套模板、两种比例、三类成片、本地草稿、作品库、再次编辑、结果缓存、任务持久化、基础限流和自动化测试。比赛版本应在这些成果上升级为面向中小制造企业的工业品智能上新 Agent。

本项目报名方向确定为 AI赋能产业服务。目标不是做一个普通修图小程序，而是把工业品照片、铭牌、规格参数和说明书转化为可审核、可追溯、可发布的主图、参数卡、卖点图和产品资料包。

## 二 与比赛要求的对应关系

比赛要求作品使用微信小程序或微信生态能力，并把大模型、Agent、RAG、AI 工作流、OCR 或多模态能力真正放进业务流程。作品还要形成场景价值、用户体验、传播运营和商业闭环。上新图的对应策略如下。

| 比赛评审维度 | 权重 | 上新图的答题重点 |
| --- | ---: | --- |
| 技术实现 | 25% | 微信登录、前后端协同、数据库、对象存储、异步任务、稳定性与自动测试 |
| AI能力融合 | 20% | 铭牌 OCR、多模态识别、说明书 RAG、工业品上新 Agent、图片生成和参数校验 |
| 创新设计 | 20% | 关键参数有来源、冲突提醒、人工审核、工业品保真和可追溯生成 |
| 场景落地与商业闭环 | 15% | 服务工厂销售和中小制造企业，按企业或任务收费，记录节省时间与修改次数 |
| 产品体验与用户增长 | 10% | 清晰的上新路径、任务进度、模板复用、分享与订阅通知、团队协作 |
| 完整性与材料质量 | 10% | 可稳定演示、真机测试、架构图、测试记录、演示视频和体验二维码 |

## 三 现有成果与缺口

### 已经完成并应保留

- 微信原生小程序与 Node.js API 已分离。
- 支持 PNG 和 JPEG 上传，支持原图、remove.bg 抠图和百炼场景生成。
- 支持三套模板、1比1与3比4比例、主图、卖点图和促销图。
- 支持品牌名、品牌色、商品大小与九宫格位置调整。
- 支持草稿、作品库、保存单张或整套、再次编辑。
- 后端已有能力预检、缓存、任务持久化和基础频率限制。
- 项目已有自动化测试，AI 不可用时可回退到原图排版。

### 比赛核心缺口

- 当前仍偏通用商品作图，工业品场景和数据模型不够突出。
- 没有正式微信登录、用户或企业空间，也没有跨设备云端作品库。
- 没有产品、SKU、规格参数、素材和审核记录数据库。
- 没有铭牌 OCR、说明书解析、RAG 检索和来源引用。
- 还没有真正的 Agent 工具编排与参数冲突校验。
- 当前本地文件存储不适合公网，没有对象存储、清理策略和完整鉴权。
- 正式 AppID、HTTPS 合法域名、隐私说明、真机回归和体验版尚未完成。
- 缺少真实用户验证、效率数据、商业模式、演示视频与完整比赛材料。

## 四 比赛版核心产品

### 核心用户

中小制造企业销售人员、工业品供应商、工厂运营人员和电商上新人员。

### 核心问题

工业品资料分散在照片、铭牌、Excel 和 PDF 中。人工制作商品资料时需要反复抄参数、修图、写卖点和检查型号，耗时且容易发生型号、尺寸、材质或图片不一致。

### 一条必须跑通的演示流程

1. 用户微信登录并进入企业工作空间。
2. 拍照或上传一个传感器、轴承、五金零件或小型设备的产品照片。
3. 拍摄铭牌或上传 PDF 说明书，OCR 和文档解析提取型号与规格。
4. 用户校正识别结果，关键字段写入结构化产品数据库。
5. 上新 Agent 调用产品数据库、知识库检索、文案生成、图片处理和一致性校验工具。
6. 系统生成工业主图、参数卡、卖点图和产品介绍，并显示参数来源。
7. 数据库与说明书不一致时给出冲突提示，不允许 AI 静默覆盖关键参数。
8. 用户人工确认后保存作品，导出一套可发布的产品资料包。

### 比赛最小可交付版本

- 微信登录与单一企业工作空间。
- 产品、SKU、规格参数、素材、任务和审核记录数据库。
- 一个工业品类的铭牌 OCR 与人工校正。
- PDF 说明书入库、检索和引用。
- 受控的上新 Agent，串联识别、检索、生成、校验与导出。
- 在现有三图基础上新增工业参数卡和企业品牌模板。
- 关键参数来源、置信度、冲突提醒和人工确认。
- 云端作品与任务进度，失败可重试且 AI 不可用时可降级。
- 正式 AppID 或体验版、HTTPS、真机测试、隐私说明和演示材料。

### 暂不进入首版

- 真实 ERP 全量对接，仅做清晰的模拟接口或 CSV 导入。
- 多企业复杂计费、完整 RBAC 和微信支付，可先保留设计与演示入口。
- 支持所有工业品类，先把一个样例品类做深。
- 复杂社交裂变和大规模运营系统，优先保证核心闭环稳定。

## 五 技术与数据方案

### 建议架构

- 小程序：微信原生框架，继续复用现有页面和 Canvas 生成能力。
- API：继续使用 Node.js，按路由、服务、数据访问层拆分。
- 数据库：PostgreSQL，比赛演示也可先用 SQLite 兼容层快速落地，但最终说明中保持关系模型清晰。
- 文件：对象存储保存原图、说明书和生成结果，数据库只保存元数据和地址。
- AI：OCR 或多模态模型识别铭牌，大模型生成文案，现有图像模型生成场景。
- RAG：PDF 解析、分块、向量检索、关键词检索和来源引用。
- Agent：只调用白名单工具，关键参数必须从结构化数据或带来源的证据中取得。

### 最小数据表

`users`、`organizations`、`memberships`、`products`、`skus`、`spec_definitions`、`sku_spec_values`、`assets`、`documents`、`document_chunks`、`generation_jobs`、`agent_runs`、`tool_calls`、`parameter_evidence`、`reviews`、`audit_logs` 和 `export_packages`。

## 六 三人分工

三块任务先由成员选择，不预设姓名。指导老师只提供业务与数据库评审，不计入三名参赛成员的开发任务。

### A 产品 小程序体验与集成

**适合人选：** 熟悉 Stitch、页面设计、产品流程和整体集成的人。

**主要责任：**

- 用 Stitch 完成比赛版信息架构和高保真页面，保留现有视觉资产并统一工业风。
- 改造首页、产品录入、铭牌校正、资料上传、任务进度、结果审核、作品库和导出页面。
- 接入登录态、云端产品与任务 API，处理加载、空状态、失败重试和降级提示。
- 完成微信分享、订阅消息入口、隐私授权提示和体验版流程。
- 负责端到端集成、演示脚本、页面截图、录屏和最终材料汇总。

**首批 Issue：**

1. 输出页面地图、用户主流程和 API 字段清单。
2. 产出 Stitch 页面并整理设计规范。
3. 新增产品录入、铭牌校正和任务进度页面骨架。
4. 改造结果页为图片、参数、来源、冲突和审核五个区域。
5. 完成真机适配与关键路径回归清单。

**验收标准：** 一名新用户能在真机上独立完成从登录到导出资料包的完整流程；所有失败状态有明确反馈；页面与演示材料一致。

**主分支：** `feature/miniapp-product-experience`

### B 后端 数据库与生产化

**适合人选：** 熟悉 Node.js、数据库、接口设计和测试的人。

**主要责任：**

- 设计 ER 图、迁移脚本和种子数据，建立产品、SKU、规格、素材、任务和审核记录。
- 实现微信登录换取会话、用户鉴权和企业数据隔离。
- 把本地 JSON 与上传目录逐步迁移为数据库和对象存储，补充清理策略与配额。
- 提供产品、文档、任务、审核和导出 API，并维护 OpenAPI 或接口文档。
- 增加幂等、限流、超时、重试、日志脱敏、健康检查和自动测试。
- 准备 HTTPS 部署、合法域名配置、环境变量模板和故障回退说明。

**首批 Issue：**

1. 提交 ER 图、数据库迁移与演示种子数据。
2. 实现登录、会话中间件和组织数据隔离。
3. 实现产品与 SKU CRUD、规格证据和审核状态 API。
4. 实现文档上传、任务状态和对象存储适配层。
5. 完成集成测试、安全检查和部署说明。

**验收标准：** 不同测试用户不能读取彼此数据；服务重启后产品、任务和作品不丢失；关键 API 有自动测试；公网演示环境只通过 HTTPS 访问。

**主分支：** `feature/miniapp-data-platform`

### C AI Agent RAG与质量评测

**适合人选：** 对大模型、多模态、RAG、提示词和自动评测感兴趣的人。

**主要责任：**

- 实现铭牌 OCR 或多模态识别，输出结构化字段、置信度和待确认项。
- 实现 PDF 解析、分块、索引、混合检索和来源引用。
- 设计上新 Agent 的白名单工具与状态机，串联产品查询、知识检索、文案生成、图片生成、参数校验和导出。
- 实现数据库值、说明书值和模型输出的冲突检测，关键参数不得无来源生成。
- 建立脱敏评测集，记录字段准确率、引用命中率、图片保真、耗时、失败率和单任务成本。
- 为 AI 不可用、超时、低置信度和内容安全失败设计降级策略。

**首批 Issue：**

1. 定义 OCR、RAG 与 Agent 输入输出 JSON Schema。
2. 完成一个工业品类的铭牌字段提取与人工校正数据回写。
3. 完成 PDF 入库、检索与来源片段返回。
4. 完成受控 Agent 流程和参数冲突检测。
5. 建立不少于 20 组脱敏样例的评测报告。

**验收标准：** 演示样例的关键参数都有来源；冲突能被发现并要求人工确认；AI 失败时基础模板仍可工作；评测报告可复现。

**主分支：** `feature/miniapp-ai-agent`

## 七 协作边界与 Pull Request 规则

- `main` 只接受 Pull Request，不直接提交功能代码。
- 开发前先建 Issue，再从各自主分支切出短分支，例如 `feature/miniapp-product-experience/plate-review-page`。
- A 主要修改 `frontend/pages`、`frontend/components` 与比赛材料；B 主要修改数据库、鉴权、API 和部署；C 主要修改 AI、RAG、Agent 服务与评测。
- 三人共同修改接口前，先在 `docs/api-contracts` 更新请求、响应、错误码和示例，接口文档先合并再写实现。
- 单个 PR 只解决一个明确问题，必须填写改动说明、关联 Issue、测试结果、截图或接口样例、风险和回退方案。
- 至少一名非作者成员审核后才能合并；涉及数据库迁移、登录鉴权和关键参数规则时需要两名成员共同确认。
- 指导老师只做方案、数据模型和业务流程评审，不作为代码负责人或第四名参赛成员。

## 八 四阶段推进计划

### 第一阶段 基线与接口冻结

- 三人完成本地运行与一次小 PR。
- A 输出页面流程，B 输出 ER 图，C 输出 AI 输入输出 Schema。
- 共同冻结产品、SKU、任务、证据和审核接口。

### 第二阶段 工业数据闭环

- 完成登录、企业空间、产品与 SKU 数据库。
- 完成产品录入、铭牌校正和云端作品。
- 选定一个工业品类与一套脱敏演示数据。

### 第三阶段 Agent与知识库闭环

- 完成说明书 RAG、来源引用和冲突检测。
- Agent 串联识别、检索、生成、校验和导出。
- 完成工业主图、参数卡和产品介绍。

### 第四阶段 比赛交付

- 完成 HTTPS、正式 AppID 或体验版、真机回归和隐私材料。
- 记录至少 5 次真实或模拟上新任务的耗时、准确率和修改次数。
- 完成项目说明、AI 能力说明、创新点、架构图、截图、测试报告、演示视频和 ZIP 包。
- 在历史说明中明确列出本次比赛新增的工业数据、OCR、RAG、Agent、审核和上线优化内容。

## 九 项目指标

- 完整流程成功率不低于 95%，演示路径可以连续稳定跑通。
- 关键参数 100% 显示来源或标记为人工输入，不允许无依据生成。
- 冲突样例 100% 给出提醒并进入人工确认。
- AI 服务不可用时仍能完成原图模板生成。
- 同一输入的重复 AI 请求优先命中缓存，避免重复费用。
- 核心 API 有自动测试，关键页面通过微信开发者工具和至少两台真机验证。
- 用脱敏样例证明上新资料制作时间和人工修改次数有所下降。

## 十 比赛提交清单

- 源代码与 README。
- 项目说明、目标用户、使用场景和核心流程。
- 微信生态与 AI 能力清单。
- 六个创新维度的说明。
- 架构图、ER 图、页面结构、关键代码与难点说明。
- 功能截图、演示视频、测试记录、体验二维码或体验版说明。
- 历史版本与本次新增内容对照表。
- 上线计划、用户增长、运营机制、商业闭环和后续路线。
- ZIP 附件按比赛要求命名，并控制在建议大小内。

## 十一 商业与作品集表达

商业模式可以先采用企业基础版加按次生成额度：基础版管理产品与模板，生成额度覆盖 OCR、RAG、文案和图片成本；企业版提供团队空间、品牌模板、批量导入和 ERP/PIM 连接器。比赛期间不必急于接真实支付，但要用真实访谈或脱敏试用记录证明谁愿意使用、为什么使用以及节省了多少时间。

面试时可将项目概括为：我在一个已有微信小程序 MVP 上完成工业软件方向升级，设计了产品与 SKU 数据模型，用 RAG 和受控 Agent 生成带来源的工业品资料，并通过参数冲突检测、人工审核、缓存、降级和自动化测试解决 AI 在企业场景中的可靠性问题。
